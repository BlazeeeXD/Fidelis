# Fidelis final architecture update — 20 November 2026

## Final design

This update separates the specialist roster from the model scheduler. The default deployment is local-first: one already-loaded OpenAI-compatible model performs four independent specialist passes sequentially. A cloud-oriented `single_pass` strategy performs all selected perspectives in one model request, and `parallel` remains available for inference servers with sufficient capacity.

The developer-facing review is delivered as one maintained GitHub pull-request issue comment. The Control Room remains the operational dashboard, while PostgreSQL remains the source of truth for results, findings, audit history and retry checkpoints.

## What changed

- **Agent selection and scheduling are separate.** `REVIEW_AGENTS` selects the independent `STATIC_ANALYSIS`, `SECURITY`, `ARCHITECTURE`, `CODE_STYLE` and/or `GENERAL` reviewers. `REVIEW_EXECUTION_STRATEGY` selects `sequential`, `single_pass` or `parallel`.
- **Sequential local inference.** Specialist calls run one after another through the same model endpoint, avoiding concurrent inference pressure on a local GPU. The default review worker concurrency is one so two PR reviews do not compete for the same local model by default.
- **Durable checkpoints.** After each successful sequential pass, the Reviewer stores validated findings and agent telemetry in the Orchestrator database. A retry restores only checkpoints with an exact SHA-256 match of the model, prompt set, selected agents, strategy, repository, commit and full review context; it then resumes at the first unfinished specialist.
- **Single-pass API mode.** One request receives the common context and all selected specialist remits and must return one results array per agent. A missing or duplicate specialist result fails the review visibly. Pipeline-level token use is counted once; per-agent rows identify shared-call execution rather than inventing independent times.
- **Parallel mode remains opt-in.** It is available for sufficiently capable inference infrastructure, not the local default.
- **Context retrieval.** The Reviewer fetches bounded source excerpts from changed files at the exact PR commit, alongside the unified diff and learned repository conventions. It does not clone or send the whole repository.
- **Finding validation.** Model findings are schema-validated and any file/line anchor must be an added line in the supplied diff. Malformed, rejected and out-of-scope candidates are counted; an all-invalid candidate set is an explicit review failure, not an empty review.
- **Model response handling.** DeepSeek-style `<think>` wrappers and fenced JSON are handled. Token-limit truncation is reported explicitly, and usage metadata is taken from the provider response rather than model-authored JSON.
- **GitHub output.** The worker creates or updates one marker-based issue comment per PR. It includes the findings, evidence locations, suggested fixes, specialist identities and execution summary. It does not flood the PR with individual inline review threads. A GitHub delivery failure is recorded separately and does not erase a completed review.
- **Control Room.** The job detail view shows the scheduler strategy, model request count, token usage, pipeline duration, reused checkpoints, specialist execution telemetry and a direct link to the GitHub report.
- **Contract v1.3.** Request/result schemas, queue dispatch, persistence defaults, generated JSON schemas/examples and documentation are consistent at version 1.3.
- **Smoke-test safety.** In LLM mode, the smoke test checks service health and active reviewer mode without creating fake PR jobs or spending model tokens. Synthetic end-to-end job/webhook smoke tests remain available in mock mode.

## Configuration

For the local DeepSeek/llama.cpp profile, merge these settings into the existing `.env`:

```dotenv
REVIEWER_MODE=llm
REVIEW_AGENTS=STATIC_ANALYSIS,SECURITY,ARCHITECTURE,CODE_STYLE
REVIEW_EXECUTION_STRATEGY=sequential
REVIEW_CHECKPOINTS_ENABLED=true
LLM_BASE_URL=http://host.docker.internal:8080/v1
LLM_API_KEY=
LLM_MODEL=fidelis-deepseek14b
LLM_TIMEOUT_SECONDS=300
LLM_TEMPERATURE=0.1
LLM_MAX_TOKENS=4096
MAX_DIFF_CHARS=48000
MAX_SOURCE_CONTEXT_CHARS=12000
MAX_CONTEXT_FILES=6
SOURCE_CONTEXT_LINES=12
REVIEWER_TIMEOUT_SECONDS=1400
REVIEW_WORKER_CONCURRENCY=1
PUBLISH_GITHUB_REVIEWS=true
```

The host model server must be running before submitting a real review and listening on an interface reachable from Docker (for example `0.0.0.0:8080`). `LLM_MODEL` must match the server's loaded model alias. Keep the real `.env` file out of source control and do not overwrite it with `.env.example`.

The GitHub token needs Pull requests: Read and Contents: Read for PR diff/source retrieval, plus Issues: Read and write to create or update the consolidated comment. Repository learning also needs permission to list merged PRs and read their changed files.

For a cloud OpenAI-compatible endpoint, set its URL, API key and model, then use `REVIEW_EXECUTION_STRATEGY=single_pass` to request one combined model generation. Use `parallel` only where endpoint/model concurrency is appropriate.

## Follow-up fix: sequential specialist JSON contract (20 November 2026)

The first live local-DeepSeek run reached llama.cpp successfully but the Reviewer rejected the `STATIC_ANALYSIS` response with `INVALID_RESPONSE` because the decoded JSON object did not contain the required top-level `findings` array. The sequential specialist system prompt described finding fields and said “Return JSON only”, but did not explicitly define the enclosing object. JSON-object mode guarantees JSON syntax, not the application's specific schema.

Changes in this follow-up:

- The sequential specialist prompt now includes the exact `{"findings": [...]}` top-level object, all required finding fields, and the exact empty-review form `{"findings": []}`.
- The prompt explicitly forbids a bare array, alternate wrapper keys such as `issues`/`results`, summaries, markdown fences and extra top-level keys.
- A schema mismatch now logs and returns the actual top-level JSON keys, making the next model-contract failure diagnosable without dumping model reasoning or source content.
- Added regression tests for the exact prompt contract and for reporting unexpected response keys.
